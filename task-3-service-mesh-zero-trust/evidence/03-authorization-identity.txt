Policies in force:
NAME                            ACTION
allow-reporting-to-ledger-api   ALLOW
default-deny-all                <none>

default-deny-all has an EMPTY spec. That is not a no-op: an ALLOW
policy that selects every workload and permits no rule denies
everything. allow-reporting-to-ledger-api then carves out exactly one
caller, one method and two paths.

----------------------------------------------------------------------
AUTHORISED   reporting -> ledger-api /transactions
----------------------------------------------------------------------
  identity: spiffe://cluster.local/ns/payments/sa/reporting
  result:   HTTP 200

----------------------------------------------------------------------
UNAUTHORISED unauthorised-client -> ledger-api /transactions
----------------------------------------------------------------------
  identity: spiffe://cluster.local/ns/payments/sa/unauthorised-client
  result:   HTTP 403

This pod is INSIDE the mesh and holds a valid certificate. It completed
the mTLS handshake successfully and was refused on identity alone.

That is the case no NetworkPolicy can express. Both pods run in the
same namespace, on the same node, in the same pod CIDR:
NAME                                   IP            SA
ledger-api-5bd7cfb845-8tk2f            10.42.0.235   ledger-api
ledger-api-5bd7cfb845-dzwmd            10.42.0.234   ledger-api
reporting-7fb448476b-q49sg             10.42.0.233   reporting
unauthorised-client-78f8b4fd9c-ndb9p   10.42.0.236   unauthorised-client

At the packet level they are indistinguishable. Only the certificate
tells them apart, and a pod cannot forge one: the private key is issued
to its ServiceAccount and never leaves its sidecar.

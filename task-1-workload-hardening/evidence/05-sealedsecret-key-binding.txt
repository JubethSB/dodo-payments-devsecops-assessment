======================================================================
 EVIDENCE: a SealedSecret is useless without its own cluster's key
======================================================================

Observed while rebuilding the cluster from scratch. The committed
SealedSecret refused to unseal:

  ==> Applying committed SealedSecret (ciphertext only)
  [warn] SealedSecret did not unseal, this cluster's controller key differs.
  [warn] Re-seal with: ./scripts/seal-secret.sh   then re-run this script.
  [fail] cannot continue without the Secret

This is the pattern working, not a bug.

WHY IT HAPPENED
----------------------------------------------------------------------
  The ciphertext in manifests/secrets/ledger-api-sealedsecret.yaml was
  encrypted to the previous cluster's controller keypair. Deleting that
  cluster destroyed the private key. The new controller generated a new
  keypair, and it cannot read ciphertext addressed to the old one.

WHY THAT IS THE POINT
----------------------------------------------------------------------
  The file is committed to a PUBLIC repository. It is safe there for
  exactly one reason: the only key that can decrypt it lives inside the
  cluster and is never exported. Anyone who clones this repo gets the
  ciphertext and nothing else, which is precisely what just happened to
  a cluster under our own control.

  Contrast with the starter, where the same credentials sat in
  deploy/deployment.yaml in plaintext. Cloning that repo gave you the
  Stripe key.

  It also demonstrates the operational cost honestly: sealed secrets are
  bound to a cluster, so disaster recovery means either backing up the
  controller's private key or re-sealing from the source of truth. That
  trade is worth making for a PCI-scoped workload, but it is a real
  trade and not a free win.

REMEDIATION IN THIS REPO
----------------------------------------------------------------------
  scripts/seal-secret.sh re-seals against whichever cluster is current.
  The Task 1 README documents re-sealing as an expected step on a fresh
  cluster rather than an error to work around.
